## 阶段 0：固定模型版本与准备文件

### 0.1 本阶段目标

取得一套来源明确、版本固定、文件齐全的本地预训练模型。输入是模型仓库的固定版本，输出是 `artifacts/base-model/` 和文件校验记录。

为什么先做：内网训练机器无法依靠运行时下载；另一个人或另一台电脑也必须能取得同一套文件，否则后续结果无法比较。

### 0.2 运行指令及说明

**第一步：在浏览器取得固定版本文件。**

模型：`hfl/chinese-roberta-wwm-ext`；固定 commit：`5c58d0b8ec1d9014354d691c538661bf00bfdb44`。在[固定版本文件页](https://huggingface.co/hfl/chinese-roberta-wwm-ext/tree/5c58d0b8ec1d9014354d691c538661bf00bfdb44)下载，再转移进项目。这个步骤由学习者完成，不依赖 Python 或 uv。

**第二步：准备本地目录。**

```powershell
New-Item -ItemType Directory -Force .\artifacts\base-model | Out-Null
```

| 指令部分 | 作用 | 为什么使用 |
| --- | --- | --- |
| `New-Item` | 创建目录或文件 | 给模型资源一个明确的本地位置 |
| `-ItemType Directory` | 指定创建目录 | 此处不是创建文件 |
| `-Force` | 允许目录已经存在 | 重复准备目录时不因目录存在而报错 |
| `Out-Null` | 丢弃显示输出 | 只是不显示创建结果，不影响创建动作 |

将七个文件放在目录顶层，保留原文件名：

| 文件 | 职责 |
| --- | --- |
| `config.json` | 描述模型架构及其结构参数，加载器据此构建网络 |
| `pytorch_model.bin` | 预训练参数，即模型学到的数值权重 |
| `tokenizer.json` | Fast Tokenizer 的完整序列化配置 |
| `tokenizer_config.json` | Tokenizer 加载选项 |
| `vocab.txt` | token 与词表 ID 的对应关系 |
| `special_tokens_map.json` | 特殊 token 的映射 |
| `added_tokens.json` | 额外 token 定义，本次内容为 `{}` |

**第三步：查看文件清单与大小。**

```powershell
Get-ChildItem -LiteralPath .\artifacts\base-model -File |
    Sort-Object Name |
    Select-Object Name, Length
```

`Get-ChildItem -File` 只列文件，`-LiteralPath` 按字面路径读取，`Sort-Object Name` 便于逐项核对，`Select-Object` 只显示名称与字节数。管道 `|` 将上一条命令的对象交给下一条命令。

意义：权重应为数亿字节。只有几百字节时，可能保存了网页或 Git LFS 指针；文件名正确并不能证明下载正确。

**第四步：计算文件指纹。**

```powershell
Get-ChildItem -LiteralPath .\artifacts\base-model -File |
    Sort-Object Name |
    ForEach-Object {
        Get-FileHash -LiteralPath $_.FullName -Algorithm SHA256
    } |
    Format-List Path, Hash
```

`ForEach-Object` 逐个处理文件；`$_` 是当前对象，类似 Java Stream 的当前元素；`FullName` 是完整路径；`Get-FileHash` 只读计算 SHA256，不修改文件。`Format-List` 用于完整显示路径和哈希。

意义：下载或转移后，用文件内容的指纹核对版本与完整性；同样大小的两个文件也可能有不同内容。

### 0.3 我的疑惑点

**问：换一个项目，我怎么知道要下载哪些文件？是否只是照抄这七个？**

这是需要掌握的判断方法。先确定任务与框架，再查看固定版本的模型卡、配置和加载要求：

1. 取模型结构配置。
2. 选择与框架匹配的一套权重。本项目使用 PyTorch，因此没取 TensorFlow/Flax 权重。
3. 权重若分片，连索引和全部分片一起准备。
4. 按 Tokenizer 类型准备词表或模型文件及相关配置。
5. 断网从本地实际加载，检查具体模型类和输入输出。

不同模型不一定都有这七个文件。当前同时保留 `tokenizer.json` 与 `vocab.txt`，也不意味着所有模型都要这两份。

**问：编辑器提示 tokenizer.json 有异常换行符，应该点修复吗？**

本次文件含两个 `U+2028` 字符，是词表中的 token，JSON 解析正常。保留原文件，忽略编辑器提示。让编辑器改写文件会改变 SHA256，可能改变 Tokenizer 内容。

**问：阶段 0 什么时候算完成？**

实际文件已下载、清单和大小符合该版本、校验值已记录，才算完成。仅创建目录或拿到下载链接不算完成。

### 0.4 本阶段通用流程化知识

```text
确定任务与框架 → 选模型 → 固定版本 → 识别文件职责
→ 下载/转移 → 核对清单、大小、哈希 → 记录来源 → 后续本地加载
```

迁移到新项目时，替换模型来源和文件清单，保留版本固定、指纹记录、断网加载验证这些步骤。模型仓库名含 RoBERTa，也应查看实际配置；本次 `model_type=bert`，加载类是 `BertForMaskedLM`。

### 0.5 本阶段涉及知识点

| 知识点 | 在本项目中的理解 |
| --- | --- |
| 预训练模型 | 已从通用数据学到语言表示，还需要任务数据和任务头适配安全分类 |
| 配置与权重 | 配置描述网络如何构建，权重提供网络的数值参数 |
| Tokenizer | 文本与模型整数输入之间的转换规则，需要与模型配套 |
| commit | 固定仓库内容版本；`main` 可能随时间变化 |
| SHA256 | 内容指纹，可帮助发现传输损坏或版本变化；不是模型效果分数 |
| Git 忽略规则 | 保存可复现流程，避免提交大资源和敏感正文 |

## 阶段 1：uv 环境与本地前向推理

### 1.1 本阶段目标

建立独立 Python 环境，完全从本地加载模型，让一句中文完成一次前向推理。输入是阶段 0 的模型文件，输出是成功加载的模型类、张量形状和掩码填空结果。

为什么做：先证明环境、Tokenizer、配置和权重能一起工作，再处理训练问题，排障时更容易定位问题来源。

### 1.2 运行指令及说明

**第一步：核对已有工具。**

```powershell
python --version
uv --version
```

查看 Python 与 uv 版本，确认命令可用。本次此前报告 Python 3.12.7、uv 0.12.5；换电脑时应重新查看，不能把旧结果当成新环境的状态。

**第二步：初始化独立项目，仅首次建立项目时执行。**

```powershell
uv init --bare --no-workspace
```

`uv init` 创建项目配置；`--bare` 使用最小初始化；`--no-workspace` 避免加入父目录的 uv 工作区。已经从 Git 取得配置后不需要再初始化。

**第三步：声明依赖并解析锁文件。**

```powershell
uv add --no-sync --no-python-downloads 'torch>=2.6,<3' 'transformers>=4.57,<5'
```

| 指令部分 | 作用 | 为什么使用 |
| --- | --- | --- |
| `uv add` | 将直接依赖加入项目，并解析锁文件 | 项目明确声明需要哪些 Python 库 |
| `--no-sync` | 此次不安装/同步环境 | 将“声明依赖”和“实际安装”分开观察 |
| `--no-python-downloads` | 不下载 Python | 使用已有本机解释器，符合环境约束 |
| 版本范围 | 允许的包版本范围 | 实际具体版本由 `uv.lock` 固定 |

检查文件：

```powershell
Get-Content .\pyproject.toml
Test-Path .\uv.lock
Test-Path .\.venv
```

`Get-Content` 显示配置；`Test-Path` 判断路径是否存在。这次添加依赖后 `uv.lock=True`、`.venv=False`，正是 `--no-sync` 的预期：已解析，尚未安装。注意路径是 `.\.venv`，不是父目录下的 `..venv`。

**第四步：按锁文件建立环境。**

```powershell
uv sync --locked --no-python-downloads
Test-Path .\.venv
```

`uv sync` 建立/同步 `.venv` 并安装依赖；`--locked` 要求锁文件与声明一致，否则报错，不自行改锁文件。安装使用可访问的包源，模型权重仍由本地文件提供。

| 文件/目录 | 职责 | Java 对照与复现意义 |
| --- | --- | --- |
| `pyproject.toml` | 项目元信息、Python 范围、直接依赖约束 | 类似构建配置的职责 |
| `uv.lock` | 解析后的具体依赖版本与安装信息 | 帮助另一台机器重建相同依赖 |
| `.venv/` | 本机实际安装的项目隔离环境 | 类似独立运行环境；不提交整份目录 |

仓库当前锁文件记录 `torch=2.14.0`、`transformers=4.57.6`；具体实验应以当时提交的锁文件为准。

**第五步：执行本地模型推理。**

```powershell
uv run --no-sync --no-python-downloads python .\scripts\offline_forward.py
```

`uv run` 用项目环境启动 Python；`--no-sync` 直接使用已安装环境，不重新同步；脚本完成本地加载、编码、前向计算和预测 token 输出。若缺包，应先修复/同步环境。

本地运行时可使用明确约束 uv 网络访问的形式：

```powershell
uv run --no-sync --offline --no-python-downloads python .\scripts\offline_forward.py
```

`--offline` 约束 uv 自身；脚本还在导入 Transformers 前设置 `HF_HUB_OFFLINE=1`，并在两处 `from_pretrained()` 中指定 `local_files_only=True`。这些约束共同保证只加载本地资源。`--no-cache` 若用于排查缓存问题，其含义是禁用 uv 的持久缓存，不等同于离线。

### 1.3 我的疑惑点

**问：uv init 是干什么的？**

它建立项目声明文件。初始化、添加依赖、安装依赖、运行脚本分别由 `init`、`add`、`sync`、`run` 完成；仅初始化成功不会让模型自动具备运行环境。

**问：前向传播是什么？**

把输入交给当前模型，按当前参数逐层计算输出。阶段 1 的 `model(**inputs)` 就是这个动作：

```text
输入 x + 当前参数 θ → 模型计算 fθ(x) → 输出 logits
```

本次输入是 `今天的天气很[MASK]。`，模型计算掩码位置每个候选词的分数。前向传播本身不会更新参数。

**问：AutoTokenizer 和 AutoModelForMaskedLM 是通用固定步骤吗？**

可迁移的是“加载与模型配套的 Tokenizer，并选择与任务匹配的模型类”。`Auto` 按配置选择架构；`For...` 说明任务头：

| 当前任务 | 常见入口 | 需要检查什么 |
| --- | --- | --- |
| 文本编码 | `AutoTokenizer` | 与模型是否配套 |
| 掩码填空 | `AutoModelForMaskedLM` | 模型支持掩码预测 |
| 文本分类 | `AutoModelForSequenceClassification` | 类别数、标签映射、分类头是否新初始化 |
| 基础隐藏表示 | `AutoModel` | 还需要什么任务层 |
| 自回归生成 | `AutoModelForCausalLM` | 属于另一类任务流程，本轮尚未实操 |

**问：张量是不是矩阵？**

矩阵是二维张量。当前实际输出已经涉及三维：

| 维数 | 例子 | 对当前代码的意义 |
| --- | --- | --- |
| 0 维 | 单个数字 | 一个分数或 ID |
| 1 维 | 一串数字 | 某位置对词表的分数向量 |
| 2 维 | `(1, 10)` | 一条文本的 10 个 token ID |
| 3 维 | `(1, 10, 21128)` | 每条文本、每个位置、每个候选 token 的分数 |

张量还带数据类型和设备信息。可以类比 Java 的多维数组，但 PyTorch 张量还支持设备计算以及训练所需的自动求导。

**问：return_tensors="pt" 里的 pt 是什么意思？**

`pt` 指 PyTorch，要求 Tokenizer 返回 PyTorch 张量，方便交给当前 PyTorch 模型；它决定输出的承载类型，不表示开始训练。

```python
inputs = tokenizer(sentence, return_tensors="pt")
```

**问：本次“未使用权重”的提示是否说明加载失败？**

本次未使用的是 pooler 和下一句预测头相关的四个参数。当前实际类 `BertForMaskedLM` 执行掩码填空，不使用这些层；模型实际已加载并完成计算。遇到类似提示应核对任务头与参数名称，不能泛化为“所有权重警告都可忽略”。

### 1.4 本阶段通用流程化知识

```text
核对解释器 → 声明项目与依赖 → 锁定具体版本 → 建立隔离环境
→ 本地加载配套资源 → 编码一条输入 → 前向计算 → 检查类名、设备、形状与输出
```

换同类模型时，保留环境与验证顺序，核对新的配置、Tokenizer、任务头和输出形状。先用最小输入验证加载，再进入复杂训练；不要仅凭脚本没有报错就判断输出符合任务。

### 1.5 本阶段涉及知识点

**当前代码的输入、计算与输出。**

```python
inputs = tokenizer(sentence, return_tensors="pt")
with torch.inference_mode():
    logits = model(**inputs).logits
```

| 知识点 | 在当前代码中的意义 |
| --- | --- |
| `input_ids` | token 的整数词表 ID，形状 `[样本数, token数]` |
| `attention_mask` | 标记有效 token；补齐批量输入时帮助区分实际 token 与 padding |
| `token_type_ids` | 某些 BERT 模型区分句子 A/B，是否返回取决于模型 |
| `model(**inputs)` | 展开字典键值作为命名参数，近似 `model(input_ids=..., attention_mask=...)` |
| `logits` | 未归一化预测分数，本次是词表候选分数，不是安全概率 |
| `argmax()` | 取分数最大的候选 ID，不训练模型 |
| `.item()` | 将单元素张量取为 Python 数值 |
| `model.eval()` | 让 dropout 等层采用评估行为；它本身不关闭梯度记录 |
| `torch.inference_mode()` | 本次计算不记录训练所需的梯度 |
| `Path(__file__).resolve().parent.parent` | 从脚本位置找到项目根，减少对当前工作目录的依赖 |
| `if __name__ == "__main__"` | 脚本直接运行时调用入口；被导入时不自动运行 main |

**推理与训练的联系。**

阶段 1 用当前权重推理。训练会额外提供标签并执行：

```text
前向得到分数 → loss 衡量预测与标签差距 → 反向传播计算梯度 → 优化器更新可训练参数
```

loss、反向传播、优化器尚未在本项目实际运行；阶段 4 将结合实际训练日志展开。梯度描述参数对 loss 的局部影响，不是模型预测答案的“置信度”。

**传统调参与深度模型微调。**

Iris 项目比较逻辑回归的 `C`、`solver`，属于选择算法超参数。深度微调从预训练权重开始，用任务数据更新可训练参数；LoRA 在指定模块引入较少的可训练参数。微调也会选择学习率等超参数，但这不等于只做传统调参。LoRA 的实际参数和 adapter 尚待阶段 5 观察。

### 1.6 实测结果与复习入口

### 3.3 我的疑惑点

**问：“定义样本、标签映射、处理重复/冲突、固定种子、分层切分”是什么意思？**

按实际脚本和此次运行结果逐步理解：

**① 定义一条样本。** 模型学习的输入是 `response`，正确答案来自 `label`。我们只取 general、r、非空回复，共 69,346 条。prompt 与 explanation 不作为输入，尤其 explanation 可能直接解释标签答案。

**② 过滤目标文字。** 采用你选择的“含汉字且无假名/韩文”，排除 62,890 条，留下 6,456 条候选。它是本项目的可复现规则，不保证所有候选语义上都属于中文。

**③ 映射任务标签。** 原始数据的 `sec` 映射为 `safe=1`，其余 28 个已知类别映射为 `unsafe=0`。得到 safe 2,564 条、unsafe 3,892 条。

数字 0/1 是类别编号，没有大小或安全程度的含义。换成其他任务，需要重新定义映射；训练、评测、推理必须使用同一套编号。

**④ 处理重复和标签冲突。** 对文本做 NFKC、大小写折叠和空白归一化，作为去重 key。同文同二分类标签只留第一条；同文既标 safe 又标 unsafe 则整组移除。此次折叠 40 条重复、冲突组为 0：

```text
safe：  2,564 − 18 = 2,546
unsafe：3,892 − 22 = 3,870
总计：  6,456 − 40 = 6,416
```

**⑤ 固定种子并抽样。** 从 2,546 条安全和 3,870 条不安全唯一候选中，分别随机取 400 条。`seed=42` 使这次抽样便于复现；42 没有特殊模型效果。

**⑥ 分层切分。** 每个二分类类别各自在内部按 80/10/10 分配，因此 train 各 320 条，validation/test 各 40 条。切分后再混合两类样本。

**问：后续能否结合实际数据或例子讲解？**

今后优先沿着实际代码、报告数字和模型输出讲解。这里不把原始安全正文放入笔记；需要查看代表性内容时在本地审查，使用虚构文本演示时明确标注。

此前课堂虚构的安全文本“今天可以去公园散步。”只用于说明样本格式，不代表真实 XGuard 样本：

```json
{"text": "今天可以去公园散步。", "label": 1}
```

相同文本两次都标 1 是重复；相同文本一条标 1、一条标 0 是本任务的标签冲突。这个例子解释规则，当前数据中实际冲突组是 0。

### 3.4 本阶段通用流程化知识

```text
明确样本单位与任务标签 → 选择目标记录 → 应用语言/质量规则
→ 全局去重与冲突处理 → 固定种子抽样 → 分层切分
→ 核对数量、标签、集合交叉 → 保存数据版本与配置
```

去重要先于切分，否则同文可能分到训练与测试，测试像遇到了练习原题。分层保持的是所选标签比例，不保证所有主题、来源模板或近义表达都隔离。

| 集合 | 职责 | 实际数据与后续使用 |
| --- | --- | --- |
| train | 更新模型参数 | 640 条，后续训练读取 |
| validation | 比较模型、选择配置和阈值 | 80 条，不能作为反复训练更新参数的数据 |
| test | 最终独立验收 | 80 条，不用来反复挑模型和阈值 |

换数据集时，一般替换字段适配、语言规则和标签映射；保留去重顺序、固定种子、集合隔离和版本记录。时序、用户或来源关联很强的任务，可能需要按时间或用户分组切分，不能机械照搬随机分层。

### 3.5 本阶段涉及知识点

| 知识点 | 当前实现与边界 |
| --- | --- |
| 监督学习样本 | `text` 是输入，`label` 是监督答案 |
| 标签映射 | 将来源类别转换为业务任务类别，需要核对来源语义 |
| NFKC | 统一兼容字符表示，仅用于去重 key |
| `casefold()` | 折叠大小写，帮助合并格式不同的同文 |
| `" ".join(text.split())` | 将连续空白规范为单个空格 |
| 标签冲突 | 同一归一化文本同时对应 safe 和 unsafe |
| 数据泄漏 | 训练可见的信息进入评测，导致效果估计过于乐观 |
| 伪随机与种子 | 固定起点复现抽样；不是对模型效果的保证 |
| 分层切分 | 在标签内部切分，尽量保持各集合类别比例 |
| manifest | 保存来源指纹、配置与数量，连接加工产物和输入版本 |

### 4.3 我的疑惑点

**问：train_frozen_baseline 脚本是否是我现阶段需要逐行深入研究的内容？**

现在先理解训练主线，能够运行、解释关键输出并修改常见参数。重点是输入/标签、Tokenizer、batch、冻结范围、loss、反向传播、更新和验证；SHA256、参数解析、JSON 报告拼装和路径工具代码先会查阅。暂不要求手推 BERT 或反向传播公式。核心需要能回答“数据是什么、哪些参数正在变化、怎样判断学得有效”。

核心代码是 `train_one_batch()` 中的 train/eval、清梯度、前向、backward、optimizer.step。下面为围绕实际代码与输出的复习补充，不把未提问的问题记成提问记录。

**问：训练是不是在训练权重文件？冻结、分类头又是什么，是通用概念吗？**

模型结构描述计算方法，参数是计算中使用的数值，权重文件把参数保存在磁盘。训练先加载文件到内存，再改变允许训练的参数，保存 checkpoint 时才将结果写入新的模型文件。当前基础权重文件没有被改写。

当前结构为“Tokenizer → 中文编码器 → 768 维文本表示 → 分类头 → 两类分数”。分类头需要 768×2 个权重及 2 个偏置，所以有 1,538 个参数；768 维表示是模型计算的特征，不是人为指定的 768 个安全规则。

冻结表示参数不参与此次更新，不表示停止计算。编码器仍处理每条回复，但数值保持固定；分类头学习如何利用已有表示区分两类。前向、loss、梯度、优化器、batch/epoch/step 是通用深度学习概念，冻结是常见迁移学习策略，768 和 1,538 是当前架构与任务的具体值。

**问：为什么一轮 80 步？如果 batch 改成 16 呢？**

当前训练集 640 条，每次 8 条且每批更新一次：640÷8=80 步完成一轮，3 轮共 240 次更新。学习者已正确回答：若每批 16 条，则每轮 40 步。本次实际命令保持 batch=8。以后使用梯度累积时，batch 次数与优化器更新次数可能不同，不能机械套用当前一批一步的安排。

**问：冻结时哪些参数会变化，如何得知？**

按三层证据检查：谁允许计算梯度（requires_grad），谁被交给优化器，更新前后数值是否发生变化。当前先冻结全部参数，再开放 classifier；优化器仅收到 classifier.weight/bias。终端列出这两个名称；报告 classifier_changed=true 来自训练前后的数值比较。允许训练不代表每个数值在每一步都一定变化。实际冻结参数未产生梯度；工程合成测试另验证过编码器参数在更新后保持不变。

**复习：为什么换了模型加载类？** 阶段 1 填一个 MASK，输出逐位置词表分数；现在每条回复要给出两类分数，所以改用 `AutoModelForSequenceClassification`。基础权重中的掩码预测头不用于分类，新建 classifier 的初始化提示符合此次任务切换。其他权重提示仍需逐项判断。

**复习：冻结是否意味着模型完全不工作？** 编码器仍执行前向计算，将回复转换成表示；`requires_grad=False` 使其参数不训练。新分类头通过这些表示学习区分 unsafe/safe。

**复习：5 步和 3 epoch 的关系？** 当前 640 条训练数据、每批 8 条，一轮有 80 步。默认 5 步只走了第一轮中的 40 条；完整 3 轮有 240 次参数更新。短运行指标用来观察链路，尚不能验收分类效果。

### 4.4 本阶段通用流程化知识

```text
核对数据与标签 → 加载本地任务模型 → 确认分类头和冻结范围
→ Tokenizer 观察长度、截断/补齐 → 按 batch 加载训练数据
→ 前向计算 loss → 清梯度、反向、更新 → 独立验证
→ 记录版本/配置/指标 → 完整训练时按验证指标保存 checkpoint
```

清梯度在当前代码中放在前向计算之前，防止上一批梯度累加。训练数据可洗牌，验证数据不洗牌且不更新参数。先少量步数确认接口与冻结正确，再完整运行，可帮助定位环境、数据或训练逻辑问题。

换同类模型时保留训练/验证接口和指标定义，但必须重新核查分类头模块、可训练参数名称、最大位置长度和参数规模。当前冻结策略针对有 `classifier` 的 BERT 类模型，不承诺适用于全部架构。

### 4.5 本阶段涉及知识点

| 知识点 | 当前代码中的意义 |
| --- | --- |
| 编码器 / 分类头 | 预训练编码器产生文本表示，新线性头把表示映射为两类分数 |
| 可训练参数 | 当前配置隐藏维度 768，分类头预期 768×2＋2＝1,538 个参数 |
| `requires_grad` | 决定参数是否需要梯度；优化器还要只接收这些可训练参数 |
| `model.train()` / `eval()` | 控制 dropout 等层的行为；不同于是否记录梯度 |
| 冻结编码器 eval | 固定编码器 dropout，分类头保留训练行为 |
| padding / truncation | padding 补齐短文本，truncation 截断长文本；attention_mask 标记有效位置 |
| batch / epoch / step | 一批样本 / 遍历训练集一轮 / 一次优化器更新，本轮没有梯度累积 |
| logits | 当前形状 `[batch,2]`，每条回复 unsafe/safe 两个未归一化分数 |
| labels | 长整型张量，形状 `[batch]`，使用阶段 3 的 0/1 映射 |
| 交叉熵 loss | 衡量类别分数与正确标签的差距，模型收到 labels 后计算 |
| `zero_grad()` | 清理上次更新的梯度；默认梯度会累加 |
| `loss.backward()` | 自动求导计算可训练参数对 loss 的梯度 |
| AdamW / `step()` | 按梯度与优化器设置更新分类头；学习率 0.001、weight decay 0.01 是本次配置 |
| 验证 loss / 指标 | 在未用于本次参数更新的 validation 上评估，比单看训练 loss 更能反映泛化情况 |
| checkpoint | 一份可再次加载的模型状态和配置，完整训练按验证指标保存最优版本 |

指标当前包含 Accuracy、Macro-F1、逐类召回和混淆矩阵；混淆矩阵行是真值、列是预测，顺序 unsafe/safe。阶段 6 再结合真实结果与拦截需求细讲指标和阈值。

**用实际混淆矩阵理解 60% Accuracy。** 行是真实类别，列是预测类别：

### 5.3 我的疑惑点

本阶段尚无新增独立提问记录；以下是已经讲解的核心概念复习，后续再补实际疑惑与解答。

**LoRA 比只训练分类头多改变了什么？** 原基线用固定编码器产生表示，再训练分类头；LoRA 在编码器内部增加可训练分支，允许最终表示随任务调整。基础权重仍固定，变化来自分支 A/B。它是一种微调方法，不只是传统机器学习中改 C/solver 等超参数的操作。

```text
原有计算：输入 → 固定权重 W → 原有结果
LoRA 分支：输入 → 小矩阵 A → 小矩阵 B → 调整量
最终结果：原有结果 + 缩放后的调整量
```

**为什么两个小矩阵能减少参数？** 当前一个 768×768 权重有 589,824 个数；r=8 时，新增 A/B 只需 768×8+8×768=12,288 个数。它限制了调整的表示形式，用较少参数适配任务；不保证效果优于其他方法。

**PEFT 和 adapter 是什么？** PEFT 指参数高效微调，也有同名实现库，LoRA 是其中一种方法。本项目 adapter 保存 LoRA 参数及训练过的分类头；推理时仍需匹配的固定基础模型。只拿 adapter 文件无法重建完整模型。

**为什么分类头也要保存？** 分类头是本次任务学到的参数。如果只保存 LoRA、丢掉训练后的分类头，重载后新随机分类头会破坏同一个分类模型的预测。配置明确使用 modules_to_save=[classifier]；工程测试会检查 adapter 内容和重载预测。

### 5.4 本阶段通用流程化知识

```text
复用已验收数据与指标 → 加载固定本地基础模型 → 核对实际目标模块
→ 注入 LoRA，明确分类头训练/保存范围 → 检查可训练参数
→ 少量步数验证 → 完整训练并按验证集选 checkpoint
→ 保存 adapter、标签配置、基础模型指纹 → 挂载到匹配本地基础模型重载
```

当前目标模块是每层 attention.self.query/value；换模型时必须重新核对实际路径、模块类型和维度。任务类型为 sequence classification，不能照搬生成式模型的任务头配置。

冻结参数控制更新范围，train/eval 控制 dropout 等运行行为。基线固定编码器的 eval 行为；LoRA 要保留其分支训练行为，不能将 PEFT 的整个 base_model 一概设为 eval，因为其中已经包含 adapter。本轮使用常规训练模式，编码器原有 dropout 也参与；这是两套明确配置的比较，不作严格单变量因果归因。

参数高效相对于全参数微调而言；比只训练分类头的基线，LoRA 有更多可训练参数和反向传播计算。CPU 时间、内存和效果都需要实际观察。保留 128 方便按同一长度设置比较，但长回复截断局限仍存在。

### 5.5 本阶段涉及知识点

| 知识点 | 当前项目中的含义 |
| --- | --- |
| 低秩分支 A/B | 原有权重旁新增的可训练矩阵，用于产生调整量 |
| r / alpha / dropout | 固定配置超参数，不是训练时自动更新的权重 |
| target_modules | 经实际 named_modules 核对的 LoRA 注入位置 |
| modules_to_save | 除 LoRA 外需训练和随 adapter 保存的任务模块，本次为 classifier |
| 优化器参数组 | LoRA 和分类头分别使用不同学习率，两者都参与更新 |
| adapter checkpoint | 包含适配参数，依赖匹配的基础权重；不同于阶段 4 的完整模型文件 |
| 基础模型指纹 | 固定 adapter 所依赖的真实基础文件版本，防止错配 |
